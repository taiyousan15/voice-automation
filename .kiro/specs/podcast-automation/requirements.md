## 1. 概要（Executive Summary）

**podcast-automation** は、毎日3テーマ（哲学・ビジネス・AI）の最新情報を自動収集・分析し、30～45分の日本語ポッドキャスト台本を自動生成して、複数プラットフォーム（Apple Podcasts、Spotify、stand.fm、YouTube、note等）に自動配信するシステムです。

**主な価値**:
- 効率: 月間90本（3テーマ×30日）の完全自動配信
- 品質: テンプレートベースで一貫した構成（導入・深掘り・まとめ）
- 拡張性: ゼロコスト版からプロレベル品質版への段階的スケール

---

## 2. 背景 & Context

### 2.1 現状の課題
- 手動ポッドキャスト制作は週3～4本の配信が限界（スケーラビリティ不足）
- テーマごとの情報収集に日次5～8時間を要する
- 複数プラットフォームへの手動配信が運用負荷を増加させる

### 2.2 既存運用
- 現在は月1～2本の試験配信のみ
- 情報源: ニュースサイト、YouTube、X（手動ブックマーク）
- 音声生成: 手動編集またはGoogle TTSの基本機能

### 2.3 解決したい問題
- 自動化により「毎日配信」を実現し、リスナー獲得を加速
- テンプレート標準化により品質バラつきを排除
- プラットフォーム統一配信で各チャネルのリーチを最大化

---

## 3. スコープ

### 3.1 In Scope ✅
- 情報収集: NewsData.io、Apify、Firecrawl等のAPI経由でニュース/ブログ/YouTube情報を自動取得
- テーマ分類: 哲学・マインド / ビジネス・マーケティング / AI関連 の3テーマに分類
- テンプレート抽出: 人気ポッドキャスト50～100件を分析し、10～20パターンのテンプレートを生成・管理
- 台本生成: 抽出した情報をテンプレートに合わせてレイアウト、Claude API（Haiku 4.5）で自動執筆
- 音声生成: TTS（テキスト音声変換）で30～45分の音声を生成（ゼロコスト版はMeloTTS、有料版はElevenLabs）
- 配信自動化: RSS生成、Spotify API、Apple Podcasts Connectへの自動登録・更新
- 複数プラットフォーム対応: stand.fm、YouTube、note、X への自動クロスポスト
- スケーラビリティ: 初期（3テーマ×1日1本）から最終（複数テーマ×複数言語への拡張）を視野

### 3.2 Out of Scope ❌
- マネタイズ: スポンサー管理、プレミアム配信、広告挿入（運用フェーズ2以降で検討）
- リアルタイム配信: ライブストリーム機能（録音・編集済みコンテンツの時間差配信のみ）
- コンテンツ編集UI: Web/モバイルアプリの作成（初版はCLIまたはAPI駆動）
- 推薦エンジン: リスナーベースの個別化推薦機能
- 多言語翻訳: 日本語専用（将来の国際展開時に検討）
- リスナーアナリティクス: ダウンロード数・再生時間の詳細分析（Podtracのような外部ツール連携を視野に）

## 4. 用語集 / Glossary

| 用語 | 定義 |
|------|------|
| **ポッドキャスト** | 定期的に配信される音声コンテンツシリーズ。RSS経由で自動配信・購読される |
| **テーマ** | コンテンツのカテゴリ（哲学・ビジネス・AI）。各テーマ独立で毎日配信 |
| **エピソード** | 1つのポッドキャスト配信単位。30～45分の音声ファイル + メタデータ（タイトル、説明、著者） |
| **台本** | エピソード生成時に使用する構成化テキスト。導入・深掘り・まとめの3部構成 |
| **テンプレート** | 台本の構造パターン（例: 「ニュース+実践例+Q&A」）。人気ポッドキャスト分析で抽出 |
| **TTS** | Text-to-Speech。台本テキストを音声ファイルに変換する技術 |
| **情報源API** | NewsData.io, Apify, Firecrawl等。ニュース・ブログ・動画メタデータを提供 |
| **配信プラットフォーム** | Apple Podcasts, Spotify, stand.fm等のポッドキャスト配信サービス |
| **RSS Feed** | ポッドキャストエピソードのメタデータ一覧。配信プラットフォームで購読用に提供 |
| **CI/CDパイプライン** | 情報収集→台本生成→音声生成→配信を自動実行するワークフロー |
| **MCP** | Model Context Protocol。Claude等のLLMと外部ツール連携用プロトコル |

## 9. 機能要件（Functional Requirements）

> すべてEARS準拠。受入テスト(GWT)と例外・エラー対応を必須。

### ===== REQ-1xx: 情報収集 =====

#### REQ-101: ニュース情報の自動取得

- 種別: EARS-イベント駆動
- 優先度: MUST
- 要件文(EARS): 毎日指定時刻（UTC 05:00）に到達すると、システムは NewsData.io API からニュース情報（タイトル、URL、概要、発行日）を自動取得しなければならない。
- 根拠/目的: 最新の市場情報をリアルタイムで収集し、 tagging・分類の基礎データとする
- 受入テスト(GWT):
  - AT-101-1: Given 現在時刻が指定スケジュール5分前 When cronジョブがトリガー Then 60秒以内にNewsData.io API呼び出し開始
  - AT-101-2: Given APIリクエスト成功 When レスポンスコード200取得 Then 最低20件以上のニュース記事が取得される
  - AT-101-3: Given ニュース取得完了 When キャッシュDB保存完了 Then レスポンスJSONの全フィールド（title, url, source, published_at）が欠損なく格納される
- 例外・エラー:
  - EH-101-1: If NewsData.io APIが応答しない（タイムアウト>30秒） then システムは alert.log に「API timeout」を記録し、前回取得済みキャッシュを使用して続行する
  - EH-101-2: If APIクエリ数が月額制限に到達 then システムはエラーメール通知し、翌月更新まで配信を停止する（自動リトライ不可）
  - EH-101-3: If レスポンスに0件ニュースが含まれる then システムは「情報不足」フラグを立て、該当テーマのエピソード生成をスキップし、前回キャッシュを使用する
- 補足:
  - 関連: REQ-102, REQ-103, REQ-301
  - NewsData.io 無料版（月1,000リクエスト）vs Pro版（月100,000リクエスト）選定は別途ADR参照

#### REQ-102: YouTube & ブログ記事の自動取得

- 種別: EARS-イベント駆動
- 優先度: MUST
- 要件文(EARS): REQ-101と同時に、システムは Apify/Firecrawl API を通じてYouTubeトレンド動画と指定ブログサイトのメタデータ（タイトル、URL、投稿日、概要）を自動取得しなければならない。
- 根拠/目的: テキストニュース以外の動画・深掘り記事を情報源に加え、多角的な情報提供を実現
- 受入テスト(GWT):
  - AT-102-1: Given Apify API呼び出し成功 When 応答コード200 Then YouTube検索結果から最低10件以上の動画メタデータ取得
  - AT-102-2: Given ブログサイトURL指定 When Firecrawl実行 Then HTML解析で記事タイトル・発行日・本文概要の取得成功
  - AT-102-3: Given 取得データ形式 When キャッシュDB格納 Then テーブル構造（url, title, published_at, source_type[youtube|blog]）一貫性確認
- 例外・エラー:
  - EH-102-1: If YouTube APIが時間制限エラー then Firecrawl APIへフェイルオーバー
  - EH-102-2: If ブログサイトが一時的に応答不可（HTTP 503）then 30秒後に自動リトライ（最大3回）
  - EH-102-3: If 指定ブログサイトのURL構造が変更 then alert.log に「Parse error」を記録。運用者は手動確認・更新
- 補足:
  - Apify無料枠: 月50,000リクエスト / Firecrawl: API別料金
  - YouTube公式APIの動画取得は制限あるため、ウェブスクレイピング併用

#### REQ-103: X / Reddit コミュニティ情報の取得

- 種別: EARS-イベント駆動
- 優先度: SHOULD
- 要件文(EARS): 毎日スケジュール実行時に、システムは X API と Reddit API 経由でテーマ関連のトレンドツイート・スレッド（いいね数・リプライ数上位）を取得し、キャッシュに保存しなければならない。
- 根拠/目的: リアルタイムなコミュニティの声・関心事を把握し、エピソード構成の最新性を確保
- 受入テスト(GWT):
  - AT-103-1: Given X APIトークン設定完了 When キーワード検索実行（例: "AI最新動向"） Then 過去24時間のツイート10件以上取得（いいね数順）
  - AT-103-2: Given Reddit API接続 When サブレディット r/japan_tech 等指定 Then 新規スレッド5件以上のタイトル・upvote数取得
  - AT-103-3: Given 複数プラットフォーム取得完了 When キャッシュ統合 Then 重複排除・タイムスタンプ付加で保存
- 例外・エラー:
  - EH-103-1: If X APIが認証エラー then alert.log記録。REQ-101のニュース情報で台本生成継続（X情報をスキップ）
  - EH-103-2: If Reddit接続断時 then エラーログ記録。次回スケジュール実行時にリトライ
- 補足:
  - X API Free tier: 月450,000ツイート検索リクエスト / Reddit: 無料アクセス（User-Agent設定必須）
  - SHOULD優先度理由: 情報源1次的にはニュースで充分。コミュニティ声は補足

#### REQ-104: 情報源の信頼度スコアリング

- 種別: EARS-状態駆動
- 優先度: SHOULD
- 要件文(EARS): 複数の情報源から取得された同一トピック情報が存在する場合、システムは各情報源の信頼度スコア（ドメイン権威度、情報鮮度、引用元数）に基づいて重み付けし、最も信頼度の高い情報を台本生成の優先情報源として選定しなければならない。
- 根拠/目的: 情報の正確性・品質を確保。複数ソース間での矛盾時に一貫性を保証
- 受入テスト(GWT):
  - AT-104-1: Given 同一トピック3件の情報取得 When スコアリング計算実行 Then 各情報源に「高(80-100)」「中(60-79)」「低(40-59)」のスコア付与
  - AT-104-2: Given スコアリング完了 When 台本生成フェーズ then スコア「高」の情報を優先段落に配置
  - AT-104-3: Given 信頼度スコア計算 When 点数=ドメイン権威×0.3+情報鮮度×0.2+クロス検証率×0.3+引用数×0.2 Then 計算結果が0～100の数値
- 例外・エラー:
  - EH-104-1: If スコアリング対象の情報源メタデータが不完全 then デフォルト値（60点）を付与し、継続
- 補足:
  - 関連: REQ-301（台本生成）、megaResearchスキル参照

### ===== REQ-2xx: テンプレート管理 =====

#### REQ-201: ポッドキャスト構成テンプレートの分析・抽出

- 種別: EARS-普遍
- 優先度: MUST
- 要件文(EARS): システムは人気ポッドキャスト50～100件を分析し、エピソード構成パターン（導入・本編・まとめの時間配分、セクション分割、トーン・スタイル）を自動抽出して、10～20個の汎用テンプレートとして保存しなければならない。
- 根拠/目的: エピソード品質の一貫性確保。テンプレートベース生成で効率化
- 受入テスト(GWT):
  - AT-201-1: Given ポッドキャスト50件以上のMP3・文字起こし取得 When 構成分析実行 Then 「導入(5-10分)」「深掘り(15-30分)」「まとめ(3-5分)」の3部構成パターン抽出
  - AT-201-2: Given テンプレート抽出完了 When JSON形式で保存 Then 各テンプレートに「パターンID」「用途」「推奨長」「セクション構成」が定義されている
  - AT-201-3: Given 10～20個テンプレート生成 When templates/podcast_templates.json保存 Then 重複排除・優先度付与完了
- 例外・エラー:
  - EH-201-1: If 分析対象ポッドキャスト取得失敗時 then 手動でサンプルを追加・補完を要求
  - EH-201-2: If 抽出パターン数が10未満 then 分析対象件数を拡大して再実行
- 補足:
  - 関連: REQ-202, REQ-301
  - 分析方法: 音声長、セクション分割、キーワード密度、トーン変化からの自動検出

#### REQ-202: テンプレートの選択・割り当て

- 種別: EARS-イベント駆動
- 優先度: MUST
- 要件文(EARS): 毎日の台本生成時に、システムは収集情報のトピック・長さ・複雑度に基づいて、REQ-201で定義した10～20個テンプレート内からプロレベルテンプレート1個を自動選択し、台本生成パラメータとして指定しなければならない。
- 根拠/目的: 情報特性に応じたプロレベルな構成で、リスナー満足度を最大化
- 受入テスト(GWT):
  - AT-202-1: Given 情報トピック=「AI技術解説」AND 情報件数=15 When テンプレート選択ロジック実行 Then テンプレートID「T-005」（深掘り重視型）を選択
  - AT-202-2: Given 情報長が少ない（5件以下）AND トピック=「速報」When テンプレート選択 Then テンプレートID「T-001」（ニュース速報型）を選択
  - AT-202-3: Given テンプレート割り当て完了 When 台本生成フェーズへ Then 選択テンプレートの「セクション構成」「推奨字数」「トーン」がプロンプトに埋め込まれている
- 例外・エラー:
  - EH-202-1: If 情報がテンプレート選択ロジックの入力条件に不一致 then デフォルトテンプレート（T-001基本型）を使用
  - EH-202-2: If 新テンプレート追加時に既存テンプレート数が20超過 then 古い使用率低テンプレート1個をアーカイブ
- 補足:
  - 関連: REQ-201, REQ-301

  - EH-503-3: If 2回連続スケジュール失敗 then 自動配信を一時停止。管理者に escalate
- 補足:
  - 関連: REQ-800, REQ-801
  - 実装例:
    - ローカル: `crontab -e` で `0 5 * * * /path/to/podcast_pipeline.sh`
    - AWS: Lambda + EventBridge ルール
    - GCP: Cloud Scheduler + Cloud Functions
  - 夏時間対応: UTC固定で実装（タイムゾーン混乱排除）

#### REQ-504: パイプライン実行時間の SLO 定義

- 種別: EARS-普遍
- 優先度: SHOULD
- 要件文(EARS): パイプライン全体（情報収集→台本生成→音声生成→配信）の実行時間を監視し、以下のSLOを維持しなければならない：
  - P50（中央値）: <90分
  - P95: <120分
  - P99: <150分
- 根拠/目的: ユーザーへの配信完了時間を予測可能に。リソース・API効率の監視
- 受入テスト(GWT):
  - AT-504-1: Given 月間実行ログ分析 When 過去30日のパイプライン実行時間統計 Then P50<90分, P95<120分, P99<150分を満たしているか確認
  - AT-504-2: Given SLO違反時 When alert 発火（P95>120分） Then 運用者に通知「Pipeline performance degradation」
- 例外・エラー:
  - EH-504-1: If パフォーマンス継続低下 then 原因調査（API遅延、TTS処理時間等）を実施
- 補足:
  - 関連: REQ-800（監視）, slo.md参照

#### REQ-800: 監視・ロギング・アラート

- 種別: EARS-普遍
- 優先度: MUST
- 要件文(EARS): システムは以下の監視項目をリアルタイムで記録し、異常値を検出した場合は自動アラート（メール / Slack）を発火しなければならない：
  - API呼び出し成功率（≥95%）
  - パイプライン実行時間（<120分）
  - 音声生成成功率（=100%）
  - 配信成功率（≥99%）
  - エラーログ出現率（<0.1%）
- 根拠/目的: 障害検出・<5秒対応。運用負荷を最小化
- 受入テスト(GWT):
  - AT-800-1: Given API呼び出し成功率=93% When 監視ダッシュボード確認 Then 「API success: 93% [WARN]」と表示
  - AT-800-2: Given success率<95% When アラート判定 Then Slack/メール通知を30分以内に送信
  - AT-800-3: Given パイプライン実行時間=140分 When 監視 Then alert「Execution time: 140 min [WARN]」
  - AT-800-4: Given エラーログ出現率=1.2% When 監視 Then alert「Error rate: 1.2% [CRITICAL]」で即座に通知
- 例外・エラー:
  - EH-800-1: If アラート機能が故障（通知送信失敗） then 管理ダッシュボードに警告表示
- 補足:
  - 関連: REQ-801, slo.md, runbook.md
  - 実装: Prometheus（メトリクス）+ Grafana（ダッシュボード）+ AlertManager（アラート）推奨

#### REQ-801: インシデント対応・ロールバック手順

- 種別: EARS-普遍
- 優先度: MUST
- 要件文(EARS): システムで障害が発生した場合、以下のインシデント対応を自動化または手動で実行可能にしなければならない：
  - Severity 1（全停止）: 初動対応 15分、復旧目標 4時間
  - Severity 2（一部停止）: 初動対応 30分、復旧目標 8時間
  - Severity 3（軽微）: 初動対応 1時間、復旧目標 24時間

  詳細な対応手順は runbook.md で管理すること。
- 根拠/目的: 障害時の対応時間を最小化。リスナー体験を保護
- 受入テスト(GWT):
  - AT-801-1: Given インシデント発生（API全停止） When runbook.md の「Severity 1」セクション参照 Then 対応手順が明確に記載されている
  - AT-801-2: Given ロールバック手順確認 When 「配信取り消し」操作実行可能か確認 Then すべての配信プラットフォームで一括取り消し可能
  - AT-801-3: Given リカバリ手順 When 「前回正常版エピソードの配信」実行 Then 該当エピソードが全プラットフォームで配信される
- 例外・エラー:
  - EH-801-1: If ロールバック処理が失敗 then 管理者にエスカレート。手動対応
- 補足:
  - 関連: REQ-800, runbook.md, adr.md
  - ロールバック対象: 台本、音声、配信メタデータ
  - バックアップ: エピソード毎に全ファイル（台本+音声+メタデータ）を30日分保持

#### REQ-802: セキュリティ・プライバシー要件

- 種別: EARS-普遍
- 優先度: MUST
- 要件文(EARS): システムは以下のセキュリティ・プライバシー要件を満たさなければならない：
  - 認証: 管理画面アクセスには多要素認証（MFA）を必須化
  - 暗号化: データベース・通信は TLS 1.2以上で暗号化
  - 秘密情報: APIキー・パスワードは環境変数/シークレット管理で保護（REQ-501参照）
  - ログマスキング: PII（個人識別情報）はログに含めない。APIキー・パスワードは自動マスク
  - 監査ログ: すべての設定変更・エピソード削除はaudit.logに記録
  - データ保持: ユーザーデータ（リスニング履歴等が実装された場合）は GDPR / 日本個人情報保護方針に準拠
- 根拠/目的: ユーザー信頼の確保。法規制への準拠（GDPR, CCPA等）
- 受入テスト(GWT):
  - AT-802-1: Given 管理画面ログイン when MFA認証が必須か確認 Then Google Authenticator / SMS等が要求される
  - AT-802-2: Given 通信ログ確認 When TLS handshake分析 Then TLS 1.2以上で暗号化されている
  - AT-802-3: Given ログ監査 When audit.log確認 Then すべての設定変更（テーマ追加、API交換等）が記録されている

- 例外・エラー:
  - EH-802-1: If MFA認証デバイス紛失時 then バックアップコード使用 or 管理者に問い合わせ
  - EH-802-2: If ログにPII発見時 then 即座に削除 + incident.log記録
- 補足:
  - 関連: REQ-501, threat-model.md, guardrails.md
  - 実装: OAuth2 + OIDC推奨、JWT トークン有効期間=1時間

#### REQ-803: スケーラビリティ・パフォーマンス

- 種別: EARS-普遍
- 優先度: SHOULD
- 要件文(EARS): システムは以下のスケーラビリティ要件を満たすよう設計されなければならない：

- 受入テスト(GWT):
  - AT-803-1: Given 初期構成（3テーマ） When リソース使用量測定 Then 月間API呼び出し数<50,000, ストレージ<100GB, 計算時間<500時間

  - AT-803-3: Given マルチ言語対応（将来） When 台本翻訳処理追加 Then API呼び出し数が 1.5～2倍に増加（受容可能範囲）
- 例外・エラー:
  - EH-803-1: If API月額上限に接近（>80%） then 管理者に通知。プラン upgrade検討
- 補足:
  - 関連: REQ-502, slo.md
  - 実装: キャッシング、非同期処理、CDN活用で効率化

### REQ-901: 月間可用性SLO

- 種別: EARS-普遍
- 優先度: MUST
- 要件文(EARS): システムは月間99パーセント以上の可用性を維持しなければならない。可用性は（正常実行日数 / 30日）× 100で計算される。ダウン時間合計は月間4.3時間以内に制限される。
- 根拠/目的: リスナーへの信頼性保証。配信スケジュール確実性を担保

- 例外・エラー:

- 補足:
  - 関連: REQ-800, REQ-801
  - 計測: CloudWatch / Prometheus で自動集計
  - 詳細: slo.md 参照

### REQ-902: コードカバレッジ要件

- 種別: EARS-普遍
- 優先度: SHOULD

- 補足:
  - 関連: tdd.md

### REQ-903: 月間運用コスト管理

- 優先度: SHOULD

## 16. セキュリティ脅威と対策

> 詳細は threat-model.md で定義。STRIDE分析の概要。

| 脅威分類 | 脅威シナリオ | リスク | 緩和策 | 対応要件 |
|---------|-----------|--------|--------|---------|
| **Spoofing** | 不正なAPI認証情報で配信実行 | 高 | OAuth2.0 + MFA | REQ-SEC-002 |
| **Tampering** | 配信中のエピソードファイル改ざん | 高 | TLS 1.2 + 秘密鍵管理 | REQ-SEC-004 |
| **Repudiation** | 管理者が「エピソード削除した」を否定 | 中 | 監査ログ完全記録 | REQ-SEC-003 |
| **Information Disclosure** | APIキーのログ出力 | 高 | 自動マスキング + シークレット管理 | REQ-501, REQ-802 |
| **Denial of Service** | API rate limit exhaustion | 中 | Rate limiting + キャッシュ | REQ-502 |
| **Elevation of Privilege** | ユーザーが管理者機能を実行 | 高 | Role-Based Access Control (RBAC) | REQ-SEC-002 |
